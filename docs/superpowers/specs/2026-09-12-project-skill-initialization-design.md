# Skillsman 项目技能初始化设计

日期：2026-09-12

状态：产品方向已确认；本文把方向细化为待审阅的接口与验收约定。尚未实施。

适用版本：下一版 Skillsman；不代表当前 CLI 已支持本文新增命令。

## 1. 产品目标与已确认决策

帮助用户在不同项目中快速初始化合适的 Agent Skills，能够从套件中只选择部分技能，复用已选组合，并在技能或模型变化后主动调整。

已在本次讨论中确认：

1. 个人高频使用优先，同时保持其他开发者可安装、可理解、可复用。
2. 持续维护预算以每月两小时为目标；不是首次开发工时估算。
3. Agent 先读取项目和用户需求，提出具体到技能名称的最小清单及理由，用户可以增减或直接指定。
4. Codex 是完整验证的主要目标，其他 Agent 延续上游安装能力，明确验证范围。
5. 项目更新由用户发起；上游新增技能不自动加入已保存的选择。
6. 初始化补齐缺失项，保留清单之外的已有技能；来源冲突和本地修改不得静默覆盖。
7. 选择可跨项目复用，各项目独立调整，不通过模板继承自动传播修改。
8. 重建保证复用技能选择并验证安装结果，不承诺恢复某天完全相同的内容。

成功体验：用户描述新项目，审阅一份有理由的最小清单后完成安装；下一个类似项目可以直接复用清单；之后能清楚看到更新范围和实际结果。

## 2. 本轮代码评估的依据

以下是本次会话的检查结果，实施前应在隔离工作区重新验证：

| 观察 | 依据与边界 | 设计回应 |
| --- | --- | --- |
| CLI 为 1,258 行 Bash，混合解析、扫描、安装与展示 | `bin/skillsman` | 保留 Bash 入口，按本次功能逐步拆职责 |
| 现有 5 项 CLI 测试通过 | `test/skillsman-cli.test.sh`；使用模拟上游 | 增加真实目录形态、部分失败和包内容验收 |
| 软链接中的技能被快照遗漏 | 临时项目中实体目录捕获 1 个，Claude 链接目录捕获 0 个并返回成功；`write_snapshot` 的 `find` 未跟随目录链接 | 使用统一库存扫描与明确的链接处理 |
| 快照只存名称和来源，按目标分组 | `write_snapshot`、`apply_snapshot`；Codex 快照不能直接应用给 Cursor | 新的可复用清单不绑定 Agent；旧快照不承担跨 Agent 清单职责 |
| 缺少 schema 的快照仍通过预览 | 临时 fixture，模拟上游清单返回空数组 | 严格校验现有快照格式，保持单一版本语义 |
| 部分库存读取错误被当作空清单 | `skill_installed_for_target`、`installed_skill_count_for_target` | 区分不存在、未知、读取失败 |
| 安装管理技能并不等于安装 CLI | `skillsman-manage/SKILL.md` 找不到命令时停止，包含个人绝对路径 | 补齐可移植的启动流程 |
| 当前工作区打包只包含 2 个自有技能 | 另外 4 个自有目录存在未提交的软链接变更；打包预览遗漏这些目录 | 先比较原有源码与链接指向内容，再恢复源码目录职责；不直接丢弃已有改动 |

未逐一验证第三方技能源当前是否仍可安装；不能把场景静态校验通过说成外部来源健康。

## 3. 范围

本版交付一条完整流程：项目识别 → 具体技能建议 → 清单预览 → 补齐安装 → 结果验证 → 清单复用；在同一数据模型上增加用户发起的选择性更新。

本版同时修复直接影响这条流程的快照、源码打包和启动问题。

暂不包含图形界面、技能市场、团队权限、后台自动更新、全网定期扫描、自动模型跑分、自动删除技能、历史版本精确恢复，也不重写全部自有技能。模型变化后的建议由 Agent 根据当前任务、技能内容和可获得的实际反馈提出，不根据模型版本号自动判定技能淘汰。

继续遵守 `AGENTS.md`：

- `skills/` 是自有技能源码，不从插件缓存复制技能。
- 场景保留简单 YAML 的 `includes`、`source`、`why`、可选 `names`。
- 场景省略 `names` 仍表示显式请求安装该来源全部技能，不能悄悄改变这一语义。
- 安装必须显式传入 `--target`，不新增全局安装功能。
- 未知目标继续传给上游，不猜测其目录。
- `all` 场景只用于审计；`--target all` 是另一概念。
- 不新增旧 schema 兼容层或命令别名。

## 4. 用户流程

### 4.1 第一次初始化

1. Agent 读取项目指令、主要项目文件和用户的任务描述。仅凭技术栈不足以推断全部技能需求。
2. 读取现有项目技能。会话中明确可见的原生能力或插件也可作为推荐参考；不可见时标记未核实，不能声称已穷尽全局配置。
3. 从现有场景中寻找候选。用户提供的来源也可作为候选，经读取真实技能目录核实名称后加入，不把来源字符串当成场景名。
4. 对整库来源先枚举候选技能，再选择具体名称。枚举失败应报告失败，不能退回整库安装。
5. 展示名称、来源、用途、选择理由、现有状态和拟执行动作。套件只充当候选入口，不自动成为安装单位。
6. 未授权安装时先展示建议；用户已明确授权具体清单和目标时直接执行，不重复询问相同授权。出现需要覆盖的冲突时先返回可审阅结果。
7. 验证安装结果，保存选择，并分别报告成功、已存在、冲突、未知和失败。

建议、计划输出使用用户语言；文档和 CLI 的公共术语保持一致。

### 4.2 复用组合

用户从项目 A 复制技能选择清单到项目 B，或以 A 的清单为输入初始化 B，并明确给出目标 Agent。

- 不复制 A 的安装状态和绝对路径。
- 修改 B 的清单不影响 A。
- 不把 A 当前所有手动安装技能自动加入可复用清单。
- 输入清单在目标项目外部时，只读取它；目标项目写入自己的独立副本。
- 不另建个人中央注册表；第一版通过普通文件和 Git 复用。

### 4.3 用户发起更新

先按项目选择清单形成具体更新范围，再读取当前来源信息和实际安装状态。

- 内容更新：只处理清单内明确选择、来源可确认且没有未处理本地修改的技能。
- 选择调整：Agent 可建议增加或移除清单项，但修改清单与卸载文件是不同动作。
- 新技能不会因为来源增加内容而自动加入。
- 已安装但不在选择清单中的技能保持原状。
- 上游检查失败显示未知；不能显示为没有更新。
- 无可信内容比较时使用“尚未核实内容差异”，不能声称有更新或已最新。
- 不后台运行，不重新执行整个来源的全量安装来实现局部更新。

## 5. 数据约定

### 5.1 场景：推荐候选

`scenarios/*.yaml` 保持现有结构，是仓库维护的候选组合。`show` 应展示现有 `why`，保留整体来源请求与具体技能请求的区别。

推荐入口不得因为某场景与项目类型匹配，就强制安装场景的全部条目。第一版无需全面拆分场景即可实现部分选择；实际使用证明过宽后再调整场景内容。

### 5.2 项目选择：用户意图

默认路径：`<project>/.skillsman/skills.yaml`。建议随项目提交到 Git。

示例使用仓库现有自有技能名称，只演示格式，不是所有项目的默认组合：

```yaml
includes: []

skills:
  - source: YatMn/skillsman
    why: 保持项目指令与 README 准确，方便后续维护。
    names:
      - skillsman-agents-md
      - skillsman-readme
```

项目清单复用场景的字段，不增加第二套技能描述语言，但采用更严格的保存约束：

- `includes` 必须为空；保存前展开候选，不保留动态继承。
- 每个来源的 `names` 必须是明确的非空列表；禁止省略和通配符。
- 顶层 `skills` 可以是空列表，此时计划为空，不调用安装器。
- `source` 和 `why` 必须是非空字符串；名称按完整字符串处理，不能按空格拆分。
- 同来源同名条目合并；同名不同来源作为冲突，不按先后顺序覆盖。
- 不保存目标 Agent、机器路径和日期对应的恢复承诺。
- 文件不存在与空清单是不同状态。前者报错，不把它解释为删除或空配置。
- 支持约定中的块列表和带引号的字符串；不支持 YAML anchors、tags、多文档和隐式继承。遇到不支持或不明确的语法直接报错，不用宽松解析猜测。
- 自己写出的文件必须能被自己的解析器无损读取。

### 5.3 安装记录：本机事实

默认路径：`<project>/.skillsman/state.json`。机器生成，通常不随项目共享。CLI 输出应提示忽略该文件，由用户或 Agent 按已有授权维护项目忽略规则。

只记录经验证的安装事实：记录格式版本、来源、技能名称、目标关联、安装内容摘要，以及上游可提供的 revision 信息。未知 revision 明确为空，不推断。

- 不储存另一份技能正文或历史包，不充当版本锁。
- 摘要覆盖技能目录内的普通文件，包括 references、scripts 和 agents 元数据；按稳定相对路径排序计算，不包含时间戳。
- 顶层技能目录链接可解析；链接断裂、循环、内部链接越界或无法稳定读取时返回未知，不写“验证成功”。
- 共享实体目录的多个 Agent 关联必须保留，不能更新一份共享内容后声称其他关联完全不受影响。
- 仅在对应安装验证成功后原子更新记录，失败项不冒充成功。
- 已有技能没有可信安装基线时，可保留并报告存在；不能自动认定它未被修改。涉及覆盖的更新需先解决该不确定性。
- 清单和状态不一致时以实际扫描结果报告漂移；不能用状态文件代替当前文件检查。

上游 `skills-lock.json` 继续作为可用的来源证据之一，由上游维护。Skillsman 不伪造、覆写其格式，也不把它当成选择清单。

## 6. 提议的命令接口

以下接口是本设计新增约定，当前实现尚不支持。保留现有命令职责，只补齐清单输入、预览和更新范围。

```bash
# 预览具体清单，不修改目标项目。
skillsman plan --file /path/to/skills.yaml --target codex --project /path/to/project

# 从清单初始化，并在目标项目保存独立选择。
skillsman init --file /path/to/skills.yaml --target codex --project /path/to/project

# 向已保存的项目选择添加具体条目。
skillsman add --file /path/to/additions.yaml --target codex --project /path/to/project

# 预览当前项目选择范围内的内容更新。
skillsman update --target codex --project /path/to/project --dry-run

# 执行已经明确授权的内容更新。
skillsman update --target codex --project /path/to/project
```

接口行为：

- `plan` 必须给 `--file`；`init` / `add` 的场景名与 `--file` 互斥。直接场景安装保留省略 `names` 的全量语义，并清楚标记这一范围。
- 从文件初始化：目标没有清单时保存副本；已有相同清单时幂等；已有不同清单时返回冲突，避免静默替换用户选择。用户可先明确修改目标清单，再初始化。
- 从文件添加：与目标清单合并；同来源重复项去重、保留原理由；冲突不自动覆盖。需要修改理由时编辑清单，不增加额外合并规则。
- `update` 本版改为要求显式目标及项目选择清单。缺少清单时给出创建选择的指引，不回退到当前的全项目更新。
- 新的清单流程使用同一计划器，执行前重新读取状态；状态变化使原计划过时时重新返回差异，不执行旧计划。
- 预览允许读取上游和使用临时缓存，但不能修改目标项目的技能、清单、锁文件或安装记录。
- 一份计划发现阻断性冲突时，整个计划在任何安装前失败。执行阶段的网络或上游失败则按第 8 节报告部分完成。
- 清单内同名技能来源未知、库存读取失败或链接损坏，都会阻断依赖该事实的计划；已确认同来源但没有内容基线的技能可以在初始化中保留，更新时仍不得覆盖。
- `status` 展示实际安装与保存选择的差异；无需为了正常状态查看调用 `doctor`。
- 旧 `snapshot` / `apply` 继续只处理当前唯一的 `skillsman.snapshot.v1`，修复扫描及校验，不混读新的选择清单。它们不承诺精确恢复历史内容，也不是推荐的跨 Agent 复用入口。
- 不增加旧快照到新清单的隐式转换、旧格式兼容或新的命令别名。

原生工具缺少可信来源或目标信息时，不能借 pass-through 承诺完整的无冲突更新；必须报告能力限制。Codex 完整验收，其他目标逐一标明实际验证范围。

## 7. 计划与状态规则

| 观察状态 | 初始化动作 | 内容更新动作 |
| --- | --- | --- |
| 没有安装 | 安装明确选中的名称 | 报告缺失并建议初始化，不借更新扩展范围 |
| 存在、同来源、基线一致 | 保留 | 有证据或明确重装授权后定向更新 |
| 存在、同来源、本地摘要变化 | 保留并报告本地修改 | 阻断覆盖，待用户解决 |
| 同名、来源不同 | 阻断并报告来源冲突 | 阻断 |
| 存在但来源未知 | 保留，报告来源未核实，不称为已满足 | 阻断覆盖 |
| 来源可确认但没有可信摘要基线 | 保留，报告内容未核实 | 阻断覆盖，不能凭当前内容补写一个“未修改”基线 |
| 清单外已有技能 | 保留，显示为额外项 | 不处理 |
| 读取失败或链接损坏 | 返回未知和具体错误 | 阻断依赖该结果的操作 |

计划最少包含目标项目、目标 Agent、输入清单摘要，以及每个技能的来源、名称、理由、观察状态、拟执行动作、证据和问题。

人类摘要优先清晰。第一版不承诺公共 JSON API 的长期兼容性；内部仍用结构化记录传递数据，避免从展示文本反解析。

安装验证成功的定义是：目标可定位技能，身份/来源证据一致，安装内容可读，记录与实际一致。它不等于 Agent 已经触发技能，更不等于技能改善了任务结果。

## 8. 架构与错误处理

保留 `bin/skillsman` 的 Bash 入口和 `install.sh`，不做整仓语言迁移。使用当前已经依赖的 Node 处理 JSON、内容摘要和必要的结构化转换。

建议随功能拆出的内部模块：

| 模块 | 职责 | 依赖边界 |
| --- | --- | --- |
| `lib/skillsman/config.sh` | 场景、选择清单及现有快照的严格读取与规范化 | 不调用安装器 |
| `lib/skillsman/inventory.sh` | 按目标批量扫描、解析链接、整理来源证据 | 调用上游只读适配接口 |
| `lib/skillsman/plan.sh` | 根据选择、库存、基线计算动作和冲突 | 不修改文件、不访问网络 |
| `lib/skillsman/upstream.sh` | 统一调用 `npx skills`，处理版本能力、超时和退出状态 | 不决定用户应该选择什么 |
| `lib/skillsman/state.cjs` | 稳定内容摘要、结构化状态读写 | 不执行安装或推荐 |
| `bin/skillsman` | 参数分发、编排、用户输出 | 不再重复实现扫描与分组 |

这些是模块边界提案，不要求一次拆完；只有相关功能触及的代码才迁移。发布包必须包含新增 `lib/` 文件，并验证脚本从安装位置和软链接入口都能定位资源。

执行规则：

1. 每个目标、每次检查阶段批量读取库存，按来源分组调用上游，避免每个技能启动一次清单查询。
2. 安装和定向内容更新仍由 `npx skills` 完成，不自行下载并覆盖技能正文。适配器仅使用已验证支持明确来源、名称和目标的调用形式；不使用裸的全项目更新实现局部更新。
3. 对已存在技能的修改前检查来源和基线。共享目录影响哪些目标必须展示；不能可靠界定影响时阻断覆盖。
4. 配置错误在安装前发现。输出错误包含失败步骤、来源、目标和下一步可执行动作，避免只报告失败退出码。
5. 执行中部分成功后失败：保留成功内容、记录经验证的成功项、保留用户意图清单并以非零状态退出；再次初始化仅补齐缺项。不得自动删除成功内容来伪装回滚。
6. 修改流程先通过原子创建 `<project>/.skillsman/operation.lock/` 获取项目操作锁；已经存在时退出并报告锁占用，不自动删除另一操作的锁。预览不创建锁。持锁期间在执行前再次核对输入和状态，使用同目录临时文件和重命名提交清单/状态；清理自己的临时资源与锁，不清理用户目录。外部编辑或状态变化被检测后中止本次提交，避免覆盖新清单或新状态。
7. 全量来源请求若要保存为可复用清单，必须拿到这次实际选择的完整名称集合和来源证据。上游不提供可信结果时报告无法保存，不把省略 `names` 写进项目清单。

## 9. 管理技能与首次启动

`skillsman-manage` 负责读取项目、解释候选与帮助用户增减清单；CLI 负责校验和执行。管理技能不得声称自己已读取环境中不可见的全部插件或技能。

启动顺序：

1. 若 PATH 中已有 `skillsman`，检查其是否支持本流程所需命令。
2. 若用户明确给出本地 Skillsman 仓库，使用该仓库的入口。
3. 否则使用项目 README 的 GitHub-hosted `npx` 入口启动 Skillsman，并验证所需能力；不要求固定的个人绝对路径，也不自动全局安装。
4. 入口下载或上游检查失败时保留已形成的建议和具体错误，说明安装未完成；不得绕过清单直接安装全套来源。

继承会话中已确认的目标、清单和授权；只对新出现的歧义、范围扩大或覆盖问题请求补充信息。安装管理技能本身的文档必须与后续 CLI 启动流程一起进行新用户烟测。

## 10. 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 全新 Codex 项目，只选择某套件的两个技能 | 只安装两项，写入明确名称和理由；来源中的其他技能不被安装 |
| A02 | 重复初始化 | 不重复安装，不新增技能，不改写无关内容，结果明确为无待执行项 |
| A03 | 从项目 A 的清单初始化项目 B | 不要求相同绝对路径；选择相同；修改 B 不改变 A |
| A04 | 上游来源新增第三个技能 | 已保存清单和普通内容更新都不自动引入第三项 |
| A05 | 项目存在不在清单内的技能 | 初始化与选择性更新均保留其文件和内容 |
| A06 | 同名但不同来源 | 预览指出两种来源，在任何安装前返回冲突 |
| A07 | 已管理技能的正文或 references 被手动修改 | 更新前识别变化，内容保持原状；无基线的已有技能显示未核实 |
| A08 | 实体目录、目录软链接、断链 | 前两种被准确扫描；断链返回问题；快照不会成功地漏记可读技能 |
| A09 | `npx skills list` 非零退出或输出损坏 | 报告读取失败，不伪造空库存，不因此触发安装 |
| A10 | 多来源安装中第二个来源失败 | 第一个来源的成功可验证，失败不写成功记录，退出非零，重试只补缺项 |
| A11 | 预览或更新预览 | 目标项目的文件树与内容前后不变；临时读取失败被明确报告 |
| A12 | 配置无效 | 项目清单缺 names、通配符、未知语法、来源缺失，以及旧快照缺 schema 均在安装前失败 |
| A13 | 保存选择与观察结果不同 | 状态输出明确显示缺失、额外或未知项；不得只按清单宣布安装成功 |
| A14 | 来源已移除被选择的技能 | 不替换成另一技能，不退回整库安装；报告无法满足该条目 |
| A15 | 新用户只安装管理技能后使用 | 无个人路径依赖，可启动 CLI 完成两项技能的临时项目初始化；离线失败不宣称成功 |
| A16 | 发布包与源码目录 | 六个自有技能及引用文件完整；模块可定位；不依赖被忽略的 `.agents/` 或插件缓存 |
| A17 | 显式整库场景安装 | 保持现有省略 names 语义；输出明确标识全量请求，与推荐的部分选择区分 |
| A18 | 其他 Agent / 共享技能目录 | 报告真实目标能力和共享影响，不假装完整兼容或隔离；Codex 安装为必须通过的完整烟测 |
| A19 | 项目清单不为空、更新未给目标或缺清单 | 参数错误清楚；不执行无范围的全项目更新 |
| A20 | 零项清单与并发变化 | 显式空选择是无操作；预览后文件或状态被改变时重新核对，不能覆盖新状态 |

推荐质量采用少量手动真实任务检查：一个代码项目、一个写作/研究项目，以及一个已经有较多技能的项目。记录用户最终增删了哪些建议、是否出现多余安装或重复确认；不新增持续运行的模型评测服务。项目类型不作为两类项目都必须安装工作流或办公技能的理由。

## 11. 实施分段与验证

### 阶段一：恢复可信基础

先比较未提交的自有技能链接内容与 Git 已有源码，在隔离工作区实施，保留用户改动。修复快照扫描和 schema 校验，补充包内容断言，集中库存错误处理。验收 A08、A09、A12 的现有快照部分、A16。

### 阶段二：初始化与清单复用

实现严格清单、计划器、文件初始化/添加、基线记录以及管理技能启动流程。保持原有场景的显式整库能力。验收 A01–A03、A05–A07 的初始化部分、A10–A18、A20。

### 阶段三：用户发起的定向更新

基于已保存选择和可信安装记录实现内容更新，处理本地修改、共享目录和不可核实的上游结果，更新 README 与管理技能。验收 A04、A05、A07、A11、A14、A18–A20 的更新部分。

每阶段先写能揭示实际失败的测试，再实现；不写只照抄内部逻辑的断言。测试结合真实临时目录和可控上游 fixture，不让单元测试依赖实时网络。

相关改动完成后执行：

- `npm test`。
- `bash -n install.sh bin/skillsman`，并对新增 Bash 模块分别做语法检查。
- 场景有修改时执行 `./bin/skillsman list`、`./bin/skillsman show <scenario>`、`./bin/skillsman coverage`。
- 检查自有 `skills/*/SKILL.md` 名称与目录相符。
- `git diff --check`。
- `npm pack --dry-run`，并核对实际包文件列表，不只看退出状态。
- 网络可用时，在临时项目用实际分发包和真实上游安装器完成 Codex 烟测。无法联网时记录未验证，不把模拟测试当作真实安装结果。

两份 README 在行为实现后同步，不能提前把提议命令写成已经可用的公共功能。具体实现任务另写计划，不在本设计阶段修改 CLI、场景或技能内容。

## 12. 设计审阅要点

本文在已确认产品方向上新增了三项具体实现选择：

1. `.skillsman/skills.yaml` 保存跨项目复用的意图，`.skillsman/state.json` 只记录安装事实。
2. 部分选择通过 `--file` 接入现有 `init` / `add`，由独立 `plan` 提供不修改项目的预览。
3. `update` 要求目标和选择清单，不再隐式更新项目的全部技能。

这些选择共同保证最小安装、可复用和可解释更新。若审阅后改变接口，先更新本设计，再形成实施计划，避免代码和文档各用一套约定。
